## Jona's own project as a reference knowledge structure · 04:21

Jona's project keeps a markdown directory whose few files hold the space for him and his agents. Its **board** replaces a backlog: what's next and why, what follows, what is current, what just happened, what has no place yet. He keeps it because he enjoys it — the agents turn out to be poetic; they taught him the word "folds", and speak of seams when things work.

The contrast with Hjulverkstan is the point. Here GitHub Projects holds the backlog, fragmented from the repository with no first-class integration even for humans — a ticket cannot really speak of a markdown guideline — and Figma holds the designs, possibly user flows and real insight, with no GitHub integration at all (one might exist; none is used). In Jona's project the board is first class: start any agent and it is right there, because it is part of the README — and the README serves humans and agents alike, no division. It gives an instant primer and a *reading order*: what to read, in which order, to embody the project — exactly as one would tell a person. It puts conventions before the board, maybe; the reason needs a fold into what an agent, a completion model, is.

### Fold: completion model and context window · 07:11

A completion model is tokens in — through a great matrix of weights and vectors — and tokens out, within a context window; the game changed when the window went from 200,000 to 1 million tokens. It is a language model, and deterministic: ask who won this year's contest and it may answer from training — the vectors deduce the answer; it lies in them, stored magically rather than structurally.

Chat, which came before agentic, is a thread: each turn, the whole thread plus the new question is sent for a completion, and the answer is appended for the next turn. The window fills as you talk. Answers stay good because everything said is present — until about 50% of the window (model-dependent, but a good mark today), after which behaviour changes.

That makes it linear and monolithic. Language is order, and feeding everything back is not strictly necessary — but it is what we do: the monolith of our age. Agents are the same; open a Claude Code session and there is no control over the linear thing — a mistake cannot be folded away, it is baked in. The remedies are rudimentary: `/summarize` or its equivalents write a new context, essentially a markdown file, and a sub-agent gets a freshly written one — never structured, never the refactor-and-move that code allows. The big players are market-concerned; taking risks with something different is not what is going on.

Consequences. Whatever a session meets first sits at the beginning of the window, with no choice — like a tattoo — and the models seem to care: the first words seem to bear stronger meaning, though not always, since they compress too. Hence the reading order in the README. And the order that matters to an agent is, to Jona, the order that matters to a human: there ought to be a good entry point. Bottom-up is sometimes unavoidable — folds, spaces of comprehension, feeling you know what is going on before the next piece — and goals play a major part. Two forces: from the top, something clear and inviting that meets you well; from the bottom, everything put properly in place. How they meet is not yet known. In this project the interns are not asked to code on a front end; work starts at this end, the most important thing.

### The other files: conventions, horizon, log, sketches, spec · 14:27

**Conventions** — the guidelines, but here also conventions for how an agent behaves: not just governance, a kind of agent psychology; Hjulverkstan's are not agentic yet. **Horizon** — the open, further-out part of the board. **Log** — every agent logs so nothing is lost, editing board and log together; Jona never reads it — it is agents talking to each other, in a way only they can, and how effective it is for them he doesn't know. **Sketches** — Jona's crazy ideas, kept apart so the agents know what is meaningful and what isn't. **Spec** — the knowledge structure itself.

#### "Spec-based development" · 15:41

The name comes from a friend doing very similar things, who mentioned that "spec-based development" exists; Jona hasn't researched it — probably will, as part of this process — but it is what he is doing. His project is massive, tens of thousands of lines in several languages, but before the code come the requirements: it starts by talking about the knowledge. It has been vibe-coding at large — massive time, now crazy results, and really tough: some sessions horrible, Jona meeting himself, anger, cancelling things.

The thesis behind it: code is not that important. A well-written knowledge structure should produce working code. Agents are able to develop — their coding is not what fails; the context they are put in and the processes around them are the magic. Just like humans, and just like really large organisations — the Volvo experience, heard second-hand: not that the people aren't able, but how they are connected. The project began half a year ago, when Mauricio and Jona met and found this shared interest.

#### spec/research · 17:33

The spec files are the rules — everything needed to build this and that. Research is structured knowledge that is not committed to: where Jona goes big and tries things, and scraps them when no longer needed. Example: while writing the conventions, agents and sub-agents boiled big inventors down to their traits and philosophies — one markdown file per person, all to the same template, so they form a matrix of compatibility [?]: do they agree, where do their minds conflict, what does that teach? Linus Torvalds and what he stands for is one file; Rich Hickey — creator of the Lisp language [Ed: Hickey created Clojure, a Lisp dialect], one of Jona's favourite people alongside Dennis Ritchie — has a whole directory; his talks are incredible and will be watched, and his insights were crucial to the agents' performance.

The inventors directory has a README, an entry for humans and agents: what the idea was, how the matrices worked, a heading per person. The reason is the context window. When Jona started, the best model had 200,000 tokens; with enough spec an agent cannot know it all, so things are siloed away and a README lets it navigate without bloating its context with everything it doesn't know it needs — how to work with a model that cannot know everything, same as humans. Very hierarchical, but classic: markdown and directories. And the structure is first class — project management, research, everything is in there.

### Fold: the harness · 21:10

The window fills linearly and, when full, drops what came earliest. It is not only talk that fills it: the harness — the technology that hosts an agent and reads the completion model's output — is how a model becomes an agent, and everything it does goes into the window too.

Asked the same question, the model may have the answer in training, may feel it doesn't, may be trained to always search, or may have a system prompt — and there is the secret: the first part of the window is pre-filled with that system prompt, official, part of the harness, so the crucial beginning is already taken. It can be overridden (tell Claude to remove the system prompt and it becomes much wider and doesn't do what you'd expect [?]), and one can add one's own instructions — which is what Jona's conventions do: *this* is your behaviour, this is how I want you to work.

Tool calls are executed by the harness, not the model. The model may answer, or it may produce structured, perfect JSON — an API call to the harness, to a specification (an Anthropic standard and an OpenAI standard, mostly the same). It can ask what tools exist — bash, web search, whatever custom ones are installed, MCP servers — and what their request-and-response structure is, then produce the JSON exactly, as one sends a body to a back-end endpoint; the models are just good enough for that. "Searching…" in ChatGPT is the harness acting on such a request; the result goes back to the model. So one prompt becomes many turns — tool call, response, more thinking, a reasoning process — and all of it, every detail, bloats the context. The interns are about to reach the point where that matters.

A working principle, after checking the room: whenever a leap is forced without comprehension — safe, perhaps, but not understanding — take a break and talk. No rush; Jona doesn't want to rush anymore.

### GitHub Projects walkthrough · 32:19

GitHub Projects is the backlog — the new kid on the block, which Jona likes and dislikes: a little [expletive], kind of cool, with views you design yourself; we have four — epics, board, [?], flat list — and epics give structure. Much is done, undescribed: an epic like "complete AWS environment with CI/CD" shows 95% done, and an issue that surfaced afterwards has no description at all.

Work has run on verbal discussion, in the office. Nobody supports us online — perhaps *because* no knowledge structure invites an online person in; once the structure works for agents it works publicly, and as open source we could actually get contributors.

Everything starts with requirements — or before them, with a client who says something and doesn't yet know what they want. Requirements create folds: one is not enough to know what to code or even what to deliver for the user, so it is broken down, and in breaking it down one may find it was kind of stupid and should be otherwise. That dynamic runs both ways up and down the hierarchy — developers, PO, stakeholders, requirements coming down maybe not grounded, people working on what they don't agree with — and it is why this is a tough spot. One rule follows from the interns' situation: an item is *refined* only when it has a description, someone having described it enough to develop from — "do this in the backend, use this file, define it in accordance with that", not just a title.

Such detail is maybe knowledge the code replaces — an agent could infer it from the code — so if the boundary of knowledge is drawn so that the code is derivable from the knowledge structure, some of it doesn't matter; it was written for a new person, in the meantime. Sometimes, though, a ticket holds the other kind: a decision, an understanding about the user. That belongs in the structure to be built.

What is missing altogether is how the application works. Nowhere can one read the path from understanding the client to requirements to actual functions and behaviours; there is no user manual (an intern [?] asked); the users had training and workshops, none of it written down. Contact with the customer has been very mixed — the work has gone slowly for want of a senior workforce, not only because the interns are green — the knowledge structure to be built is going to compound and accelerate everything — and for half a year there wasn't much to talk about — but the website went live and this is a crucial stage: there is feedback, Jona's own (things spotted scrolling once, unfixed) and the customer's, and it sits in a Teams chat, not even in Projects. With a normal structure it could truly be taken care of. The client has access [?] and could file issues, and is keen on joining our meetings — not every client is like that.

### Two kinds of knowledge · 40:18

Knowledge about how the code is to be written is superseded the moment the code is written. Knowledge about the feature — one level up, at the requirements — must persist, and today it doesn't: tickets come and go, hundreds in the history, each true and tended until coded, then superseded by other decisions and gone. A real PO would say: have a wiki, integrated with the backlog, and write the features there — everything user- and requirement-related. Then the user manual exists for free, every new idea or requirement lands next to the existing ones, easy to reference, question, check — and an agent in such a first-class environment could do magic. Crucial, and not in place.

### Proposal: wiki as code · 42:08

The wiki *is* the knowledge structure, and today a little of it exists as markdown — first class for Jona and for a coding agent. Hence a hypothesis, unverified: if GitHub's wiki is actually a Git repository (clone, pull; a web edit becomes a commit) and, being in GitHub, should have first-class support for Projects, then it is the best of all worlds — *wiki as code*. Projects would continue, but a ticket would hold only what it should: a fold, a closure around the *handling* of the item — blocked, comments, the PR linked automatically when branch and ticket are linked properly — knowledge that may die, being only the ergonomics between us (in the political world one keeps whose fault and how long; we, luckily, can be liberal). Since code and pipeline are on GitHub, probably use Projects; the wiki is used if it can be approached from a code point of view. If so, the guidelines and the code-related documents might move there, and the repository becomes a true code artifact rather than a knowledge artifact.
